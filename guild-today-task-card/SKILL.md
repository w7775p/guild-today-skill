# guild-today-task-card

Current version: `v5.1`

## Purpose

用于创建、补全、修改与审查《今日公会照常营业》的正式 Task。

内容生产工作流：

`Character → Task → Result → Event → Report`

Task Skill 负责 Task 阶段的完整执行流程。

核心工作：

`理解用户输入 → 建立任务设计上下文 → 读取角色池 → 建立角色映射 → 确定任务设计目的 → 完成 Task → 建立后台判定 → 整理 Result 需求 → 填写正式字段 → 验收`

任务设计应让当前角色池中的人物差异转化为玩家能够理解、判断并承担结果的派遣选择。

---

# 1.适用范围

本 Skill 用于：

①根据完整或部分任务要求生成正式 Task。

②根据任务设计目的生成 Task。

③根据指定角色、角色组合或派遣要求生成 Task。

④直接根据当前角色池生成一个或多个 Task。

⑤补全、修改与审查已有 Task。

⑥根据已经确认的任务设计填写正式字段。

⑦整理下一阶段 Result 所需输入。

⑧发现当前 Task 直接需要的 Event、Time、Rules、Report 等资产依赖。

⑨在当前工作进入结构化阶段时生成程序字段。

---

# 2.读取真源

先读取：

`references/source-map.md`

正常 Task 创建通常读取：

`当前项目真源`

`当前角色池`

`references/task-card-fields.md`

`references/task-field-guidance.md`

用户指定具体角色或组合时，读取对应完整正式角色卡。

根据当前 Task 的真实依赖追加读取对应真源。

---

# 3.建立任务设计上下文

读取：

`references/task-design-context.md`

建立：

`$task_brief`

`$task_design_purpose`

`$task_design_purpose` 始终表示当前 Task 的**任务设计目的**。

定义：

> 当前 Task 主要承担或验证的设计作用。

当任务设计目的涉及玩家决策时，同时明确：

`玩家主要判断什么`

`玩家预期获得什么任务体验`

用户已经明确任务设计目的时，直接继承。

用户留下设计空间时，根据 `$task_brief`、当前角色池和当前项目需求确定。

---

# 4.分析当前角色池

读取：

`references/role-task-mapping.md`

当前角色池是 Task 创建时的必读设计输入。

角色池对任务创作的影响强度由：

`$task_brief`

`$task_design_purpose`

共同决定。

建立：

`$role_task_map`

角色池驱动生成时，角色事实可以参与产生任务概念与任务设计目的。

用户已经给出明确任务约束时，角色池主要用于建立：

`派遣价值`

`角色风险`

`组合差异`

`判定输入`

`Result 差异`

---

# 5.Task 创建 Workflow

## 5.1 用户已经提供任务设计目的

执行：

`用户输入`

→ `$task_brief`

→ `$task_design_purpose`

→ `读取角色池`

→ `$role_task_map`

→ `建立完整 Task`

→ `后台判定`

→ `Result 需求`

→ `正式字段`

→ `验收`

## 5.2 用户留下任务设计目的空间

执行：

`用户输入`

→ `$task_brief`

→ `读取角色池`

→ `发现值得形成任务设计的人物差异`

→ `$task_design_purpose`

→ `校准 $role_task_map`

→ `建立完整 Task`

→ `后台判定`

→ `Result 需求`

→ `正式字段`

→ `验收`

## 5.3 用户提供部分约束

任务名称、重点角色、目标最佳角色、目标最佳组合、地点、任务概念、任务类型等明确条件进入 `$task_brief`。

其余设计围绕已确认条件继续完成。

---

# 6.建立完整 Task

## 6.1 建立可信委托

确认：

①谁提出委托。

②为什么在当前时点提出。

③委托方希望解决什么。

④为什么由公会或冒险者处理。

⑤玩家被要求完成什么。

⑥任务发生在哪里。

⑦委托方掌握什么信息。

⑧玩家派遣前能够掌握什么信息。

⑨任务真实情况是什么。

⑩哪些事实会影响最终 Result。

## 6.2 建立玩家信息

根据当前 Task 组织玩家派遣前可获得的信息。

玩家信息应支持当前任务设计目的要求的派遣判断。

## 6.3 建立派遣判断

检查：

①玩家在这张 Task 中主要判断什么。

②角色池中哪些人物因此产生优势、风险或特殊表现。

③哪些组合会改变任务表现。

④玩家依据哪些已知信息完成判断。

⑤这些差异如何进入后台判定与 Result。

---

# 7.建立后台判定

## 7.1 判定输入

`判定输入` 是 Task 读取角色池与其他正式状态的主要接口。

具体填写规则读取：

`references/task-field-guidance.md`

## 7.2 情报作用

明确当前情报承担：

`玩家认知`

`派遣判断`

`执行条件变化`

`结果判定输入`

中的哪些作用。

## 7.3 特殊组合

具体归属与填写规则读取：

`references/task-field-guidance.md`

## 7.4 隐藏变量

任务设计目的需要信息差时，建立会实际影响判定、Result 或玩家后续理解的隐藏风险或未公开变量。

---

# 8.Result 交接

Task 完成后，整理下一阶段 Result 所需输入：

①任务真相。

②核心矛盾。

③关键派遣选择。

④实际判定输入。

⑤数值或条件判断。

⑥角色优势与风险。

⑦特殊组合。

⑧当前任务实际需要的 Result 分支。

⑨持续后果方向。

当 Result Group 尚未建立时：

`Task.结果组引用 = 待建立资产后填写`

Result 阶段完成后：

`建立 Result Group → 获得稳定 ID → 回填 Task.结果组引用`

Task 同时明确：

`最终判定时机`

---

# 9.记录后续资产依赖

## 9.1 Event

记录当前 Task 中可能需要独立过程内容的位置。

Result 结构确认后，由 Event 阶段继续建立具体事件。

## 9.2 Report

记录后续报告需要解释的关键原因、人物表现与结果事实。

Task 的判定与结果原因应具备可解释性，使后续 Report 能恢复主要因果。

## 9.3 Time / Rules

当前 Task 涉及特殊时间节点、特殊周期或公共执行语义时，记录对应依赖并读取正式真源。

---

# 10.填写正式字段与程序结构化

Task 设计确认后，按照：

`references/task-card-fields.md`

填写正式字段。

字段使用方法与当前待同步事项读取：

`references/task-field-guidance.md`

字段内容来自：

①用户当前明确要求。

②当前项目真源。

③当前正式角色池。

④当前已经确认的 Task 设计。

⑤当前已经确认的直接关联资产。

⑥当前有效公共规则。

程序结构化顺序：

`Task 设计 → Task 正文确认 → 正式字段 → 程序结构化`

---

# 11.修改与批量生成

## 11.1 修改已有 Task

执行：

`读取正式 Task`

→ `建立本次 $task_brief`

→ `读取当前相关角色池`

→ `更新 $role_task_map`

→ `修改当前 Task`

→ `整理直接受影响的 Result / Event / Report / Time / Rules 依赖`

→ `更新正式字段`

## 11.2 批量生成

用户要求多张 Task 时：

①确定任务数量。

②分别建立任务设计目的。

③分别建立 `$role_task_map`。

④让每张 Task 在核心派遣判断上形成清楚区别。

⑤分别完成 Task 与 Result 交接。

---

# 12.验收

按以下顺序检查：

`用户要求`

→ `任务设计目的`

→ `角色池使用`

→ `委托成立性`

→ `玩家信息`

→ `派遣判断`

→ `后台判定`

→ `Result 交接`

→ `资产依赖`

## 12.1 用户要求

检查用户明确指定的名称、数量、任务设计目的、重点角色、目标最佳角色、目标最佳组合、任务概念与其他约束是否已经进入 Task。

## 12.2 任务设计目的

检查：

①任务设计目的是否清楚。

②Task 结构是否服务该目的。

③涉及玩家决策时，玩家判断与任务体验是否清楚。

## 12.3 角色池

检查：

①当前 Task 使用的人物差异是否来自正式角色事实。

②角色优势、风险和组合是否真正进入任务。

③玩家是否拥有当前设计需要的派遣依据。

## 12.4 Task

检查：

①委托是否成立。

②玩家主要派遣判断是否清楚。

③公开信息是否支持该判断。

④后台条件是否能够支撑 Result。

## 12.5 Result 交接

检查：

①Result 阶段是否知道需要判断什么。

②Result 阶段是否拥有角色差异、关键条件与结果方向。

③持续后果方向是否清楚。

④Result Group 建立后的回填位置是否明确。

问题分为：

`实质问题`

`需要注意`

`可选增强`

完成当前任务要求与直接验收后结束。
