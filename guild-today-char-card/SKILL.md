# guild-today-char-card

版本：v5.1

生成可由用户继续修改的角色草案，完成字段组织、事实核对、格式转换与授权发布。保留设计目的优先、人物进入玩法和公共规则独立的原则。

`确定任务 → 读取所需真源 → 保留核心设定 → 创作或定点修改 → 分类检查 → 按授权交付`

# 1.确定任务与边界

| 任务 | 执行范围 |
|---|---|
| 创建、补全 | 根据给定核心主动创作，交付可编辑草案。 |
| 局部修改 | 修改指定内容及当前卡内的直接影响，保留其他正文。 |
| 重构 | 允许改变结构与开放内容，保留用户明确指定的身份、冲突、关系和结局安排。 |
| 审查、讨论 | 提供问题与建议；未经授权不修改资产。 |
| 排版、升版本、发布 | 使用用户指定底稿，保留文字与设定；补写需要另有明确授权。 |
| 程序结构化 | 仅在正文确认且用户要求时执行，逐条追溯正文。 |

动笔前内部记录当前角色、任务、设计目的、输出形式、修改范围和必须保留的设定。用户已说清的内容直接执行，无需重复询问或逐项展示内部记录。

只有核心设定冲突、输出指令存在实质歧义、外部写入目标或权限不明确时提问。暂停受影响部分，继续其余已明确工作。

# 2.读取真源与人工底稿

先读 [真源映射](references/source-map.md)，按领域取得当前有效资料。填写或审查字段时完整读取 [字段口径](references/character-card-fields.md)。

①用户当前决定优先；用户指定的人工修订稿是本轮角色底稿。其他事实从对应领域真源取得。

②创建或重构时确认项目规则、当前角色池及直接相关角色。纯格式转换已有完整底稿时，只核对目标格式和影响正确性的资料。

③字段快照正常可直接使用。用户要求最新口径、发生冲突、涉及未冻结规则或维护快照时，读取其对应当前真源；维护快照保留真实来源日期。

④同一任务内复用已完整读取且仍有效的资料。新事实、版本冲突、用户提示改稿或执行外部写入时，重新读取相关来源。

⑤保留人工删除、措辞调整与字段重排。后续生成不得恢复已删内容、将旧稿覆盖新稿，或把推测标记自动移除。无法判断两份稿件谁有效时，只询问冲突部分。

# 3.保留设计核心

从用户输入和有效底稿提取身份、动机、主要冲突、关键关系、固定数值、触发阈值、结局边界与禁止项。用它们检查正文，不把它们变成额外的角色字段。

泛式示例：用户要求保留某项职责、秘密行动及到期离开安排，重构时必须保持三者的因果关系；可以补充执行方式与日常表现。

明确区分设计目的与叙事定位：前者说明预期玩家体验，后者按字段口径说明人物在世界或故事中的位置。

人物可以简单、复杂、透明、神秘、稳定或变化。隐藏面、弱点、关系、争执和成长按设计目的使用。保持人物的缺点与矛盾；改变价值观、走向和解或增加创伤解释都需要人物依据。

# 4.主动创作与推测

①在开放创作范围内补充日常、经历、语言、行为与生活需求。普通创作属于草案，无需每句附加标记。

②补齐明确缺失的职业、经历节点、时长等关键项时，给出具体候选并附“（推测）”。用户要求保留占位文本时逐字保留；无法区分占位要求与补写要求时先确认。

③公开职业、行为倾向与能力限制各有含义。性格倾向升格为绝对限制需要明确依据；角色保有理解情境、作出选择和必要交流的能力，除非用户另有设定。

④隐藏面可以来自持续欲望或价值取向。检查好的一面与阴暗面能否同时成立，避免自动补成伪装或创伤补偿。

⑤持续承担人物内容的角色应有足够的任务外生活。只补与人物有关的部分；缺少生活基础时说明影响，保持其余工作继续。

⑥用户明确指定的私人关系按双方事实展开。未经指定的新关系作为候选标注，不能自动写成对方的既定事实。无需为了对称补出关系收益。

⑦公共公式、统一状态、世界制度和独立事件正文读取所属真源。尚未确认的部分保持未确认；用户允许补写假设时明确标注，假设只服务当前草案。禁止以角色卡发布替代公共规则定案。

# 5.人物行为与派遣判断

## 5.1 建立一致的因果

按需要检查：

`常态倾向 → 触发情境 → 行为变化 → 玩家可见反馈 → 后果`

持续欲望与失控条件分开描述；触发、加剧、抑制和揭露阶段相互对齐。触发后果不自动等于玩家立即获得全部秘密。

稳定型人物可以直接采用“原则 → 行为”，无需强制拥有完整隐藏链。

## 5.2 正确归类

| 情况 | 字段归属 |
|---|---|
| 接受委托前拒绝 | 派遣前拒绝 |
| 没有相关命令，自行补充行动 | 自主行动 |
| 收到明确命令后选择违反 | 任务中违抗 |
| 完成原任务，未额外提供帮助 | 隐藏面、行为优先级与任务结果 |
| 任务结束后自行处理私人事务 | 任务后自发行为 |

违抗必须写清被违反的命令。抑制措施应具有玩家可控因素与合理代价；检查其是否只剩绕过条件的操作技巧。

角色卡只维护个人事件的引用、概要与触发意图。独立资产建立后，完整事件正文由该资产维护。

## 5.3 检查收益与风险

说明玩家为什么想派这个角色、何时会犹豫，以及差异如何进入任务、报告或持续后果。

把能力收益、资源成本、关系影响及长期风险一起判断。单项任务最佳人选可以成立；未实测的平衡问题记为测试问题，不据此改掉用户固定数值、组合收益或触发阈值。

通用重复任务只检查角色的派遣价值；唯一任务再结合自身决策目的检查。任务过程默认不可见，提前反馈需要实际通讯或事件渠道。

# 6.填写与格式

角色 ID 固定采用 `hero_xxx`，后缀为稳定的小写英文标识，校验模式为 `^hero_[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`。这里的后缀表示命名格式，正式角色应使用真实稳定标识，不能把占位内容当成有效身份。

①同一角色改名、改稿或升版本保持 ID。发现旧 ID 不合规范时列出旧新映射与引用影响，只在授权范围内统一迁移；禁止只改单页导致断链。

②角色卡名称使用“角色名_角色卡v版本号”。版本号来自用户要求或当前版本延续，避免创建重复页面。

③数值、简要描述与详细描述准确取自字段真源。原文中的特殊措辞与专名保持原样，不能改写成人物专属描述。

④完整新卡沿用 [十模块模板](assets/character-card-template.md)。已有人工版式在局部修改时保持；用户明确要求统一版式时才转换。十模块是展示结构，字段的定义与可见性仍由字段口径负责。

⑤必填字段按口径承载。选填与特殊字段只在有内容时使用，避免为填表制造机制。自动字段交给系统，正文注明来源即可。

⑥维护同一条规则的主要位置；其他模块保留必要概要或引用。避免多处重复描述导致修改不同步。

⑦采用清晰的标题与表格，枚举使用“①内容”。默认遵守用户的篇幅与输出形式。

# 7.检查与辅助工具

工具只做机械检查，人物判断由正文审查完成。

| 检查 | 可报告的结论 |
|---|---|
| ID、字段、数值原文、模块结构 | 格式检查结果与具体错误 |
| 核心设定、因果、关系、可见性 | 文案一致性判断及依据 |
| 外部写入与回读 | 实际写入范围及内容核对结果 |
| 玩家理解与玩法平衡 | 实际测试结果；未测则明确未测 |

禁止用统一的“角色验收通过”代替这些不同证据。只输出对本次任务有影响的检查结果。

## 7.1 文案工具

使用 Python 标准库脚本 [card_tools.py](scripts/card_tools.py)。脚本读取当前字段快照，不另存数值字典；如果本轮使用更新真源，应通过 `--fields` 提供对应快照。

```bash
python scripts/card_tools.py check 角色草案.md
python scripts/card_tools.py check 角色草案.md --partial
python scripts/card_tools.py render-notion 角色草案.md
python scripts/card_tools.py compare 原稿.md 回读稿.md
python -m unittest discover -s tests -v
```

命令默认只读输入并输出结果，不覆盖文件，不联网，不写 Notion。格式转换仅处理受支持的表格，保留正文；遇到不支持结构返回错误，不能静默丢失内容。对外保存仍需按用户授权与相应工具规范执行。

脚本检查失败时修正机械问题或报告明确限制。不能为消除检查提示而创造缺失的人物事实。

## 7.2 迭代验证

仅在维护本 skill 时读取 [泛式回归案例](references/regression-cases.md)。用任务原始输入做独立验证，把评审要求留在评审侧。验证不得修改真实角色池或未经授权的仓库；发现问题后只修正有证据的部分。

# 8.外部发布与关联影响

①用户要求聊天输出时，直接在聊天交付。写入文件、Notion 或仓库时遵守指定目标和范围。

②写入前读取目标最新内容、ID及版本。把人工改动合入底稿；存在不可消解冲突时暂停相关写入。

③仅发布获授权角色及必要索引。关联角色、任务、事件和结果的影响只列出；用户授权相应资产后再修改。自行告知要同步不能替代授权。

④Notion 使用当前工具支持的原生标题与表格。保留子页、属性和无关内容；局部更新使用准确替换区域。避免用全文覆盖处理小修改。

⑤保存完整推测标记。发布成功不使假设转为已确认事实。权限、审批或受保护流程构成停止条件，不能更换通道绕过。

⑥写后回读并核对正文、数值描述、推测标记、版本及必要索引。转换前后比对正文；报告实际完成与未完成项，不把技术保存等同于设计验证。

# 9.交付结束

优先交付用户当前需要的正文、局部修改或发布链接。只补充影响使用的冲突与未确认项；完成后停止。

示例与测试使用泛式角色称谓和关系类型，不植入项目具体人物。正式角色卡按当前任务中的真实角色资料生成。
