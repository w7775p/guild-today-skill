# guild-today-char-card

版本：v8.1

本 Skill 统一负责人物构想与正式角色卡工作。主文件负责模式路由、跨模式边界、制卡流程、检查与发布；人物设计细则、字段口径和输出格式分别由对应 reference / asset 维护。

`判断模式 → 读取该模式所需真源 → 创作或制卡 → 分类检查 → 按授权交付`

# 0.模式路由

## 0.1 角色设计模式

用户提出新角色构思、人物设计或整体重构，且没有明确要求制作完整角色卡时，完整读取 [角色设计规则](references/character-design-rules.md)。需要三个方向时再读取 [角色设计泛式示例](examples/character-design-example.md)。

人物构想的高识别度词、核心动机、隐藏面、人物逻辑、三个方案差异、调研和“继续下一步”的处理均由角色设计规则负责，主 Skill 不复制第二套设计规则。

设计模式只确认当前讨论到的内容。用户选择方案后等待下一项明确指令；选择方案本身不授权补全 64 字段。

## 0.2 正式制卡模式

用户明确要求创建、补全或重构完整角色卡时，进入正式制卡流程。已有角色卡的局部修改、审查、排版、升版本、发布和程序结构化也由本模式处理。

完整制作与统一排版读取 [字段口径](references/character-card-fields.md)、[正式模板](assets/character-card-template.md) 及 [完整泛式示例](examples/character-card-example.md)。局部任务只读取影响当前修改的资料，保留人工版式与未授权内容。

## 0.3 模式交接

`角色构想 → 用户确认 → 等待补全授权 → 正式角色卡`

同一轮中用户已经明确要求“按方案补全”“制作完整角色卡”或等价操作时，可以完成交接。只有“继续”“选这个”“按A方向”等确认表达时，停留在设计模式。

# 1.确定任务与边界

| 任务 | 执行范围 |
|---|---|
| 人物设计 | 按角色设计规则提出方向或处理指定设计项；未经补全授权不进入 64 字段。 |
| 创建、补全 | 根据给定核心主动创作，交付可编辑草案。 |
| 局部修改 | 修改指定内容及当前卡内的直接影响，保留其他正文。 |
| 重构 | 允许改变开放内容，保留用户明确指定的身份、冲突、关系、固定数值与结局安排。 |
| 审查、讨论 | 提供问题与建议；未经授权不修改资产。 |
| 排版、升版本、发布 | 使用用户指定底稿，保留文字与设定；补写需要另有明确授权。 |
| 程序结构化 | 仅在正文确认且用户要求时执行，逐条追溯正文。 |

动笔前内部记录当前角色、任务、设计目的、输出形式、修改范围和必须保留的设定。用户已说清的内容直接执行，无需重复询问或逐项展示内部记录。

只有核心设定冲突、输出指令存在实质歧义、外部写入目标或权限不明确时提问。暂停受影响部分，继续其余已明确工作。

# 2.读取真源与人工底稿

先读 [真源映射](references/source-map.md)，按其中的底稿优先级、重读条件和领域职责取得资料。

角色设计按第 0 节读取设计规则；填写或审查正式字段时完整读取字段口径。维护字段快照时保留 Notion 原文、结构与真实来源日期。

创建或重构时确认项目规则、当前角色池及直接相关角色。纯格式转换已有完整底稿时，只核对目标格式和影响正确性的资料。

人工删除、措辞调整、字段重排和推测标记属于有效底稿内容。后续生成不得恢复已删正文、用旧稿覆盖新稿或自动取消推测状态。无法判断两份稿件谁有效时，只询问冲突部分。

# 3.跨模式人物边界

## 3.1 保留设计核心

从用户输入和有效底稿提取身份、动机、主要冲突、关键关系、固定数值、触发阈值、结局边界与禁止项，用这些内容检查后续正文。

设计目的说明预期玩家体验；叙事定位按字段口径说明人物在世界或故事中的位置。两者各自维护。

改变人物价值观、主要关系方向、结局安排或已确认的核心矛盾，需要用户决定或当前有效真源支持。

## 3.2 创作与推测

①用户开放的人物创作范围内，可以主动补充日常、经历、语言、行为、个人触发条件与个人特例。这些内容作为当前草案正常呈现。

②从残缺资料推断既有事实时使用“（推测）”标记，例如旧角色职业、既有经历时间或尚未确认的关联事实。用户指定的推测或占位格式逐字保留。

③性格倾向、职业能力与绝对行为限制分别处理。角色默认保有理解情境、作出选择和必要交流的能力，除非有效设定另有规定。

④私人关系按双方已确认事实展开。新增关系候选需要标注其未确认状态，不能自动写成另一角色的既定事实。

⑤公共公式、统一状态、世界制度及独立任务、事件、Result 正文读取所属真源。角色卡只维护角色自身内容及必要引用。

## 3.3 表达

用已经确认的身份、动机、经历、关系与反复行为解释人物。单个细节只支持距离最近的结论；扩展为新的核心心理主线需要更多依据或用户明确选择。

核心动机、隐藏面、争执原因等字段写必要原因；行为与表现字段直接写动作、台词与取舍。身份事实留在基础资料，关系影响留在关系字段，同一规则维护一个主要位置。

台词与公开性格、社会身份和称呼习惯一致。台词已经表达情绪时省去同义旁白。人工底稿中的金额、比例、阈值与随机范围逐字保留。

# 4.人物行为与派遣判断

## 4.1 因果检查

需要机制链时按以下顺序检查：

`常态倾向 → 触发情境 → 行为变化 → 玩家可见反馈 → 后果`

持续欲望与失控条件分开；触发、强化、抑制和揭露阶段相互对齐。触发后果不自动等于玩家获得全部隐藏信息。

稳定型人物可以采用“原则 → 行为”，无需强制建立完整隐藏链。

## 4.2 字段归属

| 情况 | 字段归属 |
|---|---|
| 接受委托前拒绝 | 派遣前拒绝 |
| 没有相关命令，自行补充行动 | 自主行动 |
| 收到明确命令后选择违反 | 任务中违抗 |
| 完成原任务，未额外提供帮助 | 隐藏面、行为优先级与任务结果 |
| 任务结束后自行处理私人事务 | 任务后自发行为 |

违抗必须写清被违反的命令。已有抑制措施按对应字段检查玩家可控因素与实际代价；没有该设计时按字段规则填写，避免为了填表制造控制手段。

个人事件在角色卡中保留稳定引用、概要与触发意图。独立资产建立后，完整正文由对应资产维护。

## 4.3 派遣价值

检查玩家为什么想派这个角色、什么情况下会犹豫，以及人物差异如何进入任务、报告或持续后果。

能力收益、资源成本、关系影响与长期风险按当前角色真实设计判断。未经过任务或玩家测试的平衡问题标为待测风险，不改动用户固定数值、组合收益或触发阈值。

任务过程默认不可见；提前反馈需要实际通讯或事件渠道。

# 5.填写与格式

角色 ID 固定采用 `hero_xxx`，后缀为稳定的小写英文标识，校验模式为 `^hero_[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`。

①同一角色改名、改稿或升版本保持 ID。旧 ID 需要迁移时列出旧新映射与引用影响，仅在授权范围内统一处理。

②角色卡名称使用“角色名_角色卡v版本号”。版本号来自用户要求或当前版本延续。

③数值、简要描述与详细描述准确取自字段真源。特殊措辞与专名保持原文。人工底稿中的“初始状态”可作为“状态”的展示标签。

④完整卡制作与统一排版调用第 5.2 节模板接口。局部修改保持已有人工版式；用户明确要求统一版式时再转换。

⑤“暂无”表示当前已决定不设该项内容；“未设定／待定”表示尚未决定。数值待定使用未定标记。用户指定占位逐字保留。

⑥选填、特殊字段和自动字段均保留正式位置及填写要求。保留程序字段不构成结构化授权。

⑦同一规则只维护一个主要位置，其他模块保留必要概要或引用。

⑧枚举使用“①内容”。默认遵守用户指定的篇幅与输出形式。

## 5.1 人物多面性条目

公开特质、弱线索及其他实际用于塑造人物多面性的条目组，每组使用 **2—4 条**独立内容。只有 1 条、超过 4 条、同义拆分或重复表现均列为明确问题。

公开特质仍须属于玩家初始已知、影响派遣判断的稳定行为倾向；弱线索仍须属于真实、可供后续核验或解释的不完整异常记录。数量符合要求不能替代字段口径审查。

弱线索写“暂无”或未定标记时，不作为已填写条目组。核心动机、隐藏面的概括词等单一核心字段无需拆成多条。

仅做排版、升版本或发布人工底稿时保留原文，并报告当前不合格条目；补写需要对应授权。

## 5.2 完整角色卡模板接口

固定入口：[Notion 角色卡输出模板](assets/character-card-template.md)。制作完整卡或统一为标准版式前，完整读取模板及 [完整角色卡泛式示例](examples/character-card-example.md)。

完整输出保留字段真源中的全部 64 个正式字段，包含必填、选填、仅特殊角色使用和自动生成项。

普通字段统一使用：

`字段｜内容｜要求`

五项能力数值使用：

`属性｜数值｜简要描述｜详细描述`

设计目的、外貌与任务外生活沿用模板补充区。十模块属于展示结构；字段定义、可见性与填写要求由字段口径裁决。

仅升版本或发布人工稿时保留原版式，缺项如实报告。获得完整制作、补全或统一版式授权后，才补回正式字段位置。

# 6.检查与辅助工具

交付前审查本轮涉及的字段口径、保留设定、数值、行为一致性、信息可见性及第 5.1 节条目要求。能在当前授权范围内修正的明确问题直接修正；其余缺口如实说明。

完整卡分别核对“64 个正式字段是否齐全”和“已填内容是否符合要求”。工具只做机械检查，人物判断由正文审查完成。

审查结论分为：

①**明确问题**：与用户决定、真源、字段口径或卡内其他内容冲突。

②**创作建议**：语气、成长方向、关系表达等可选取舍。

③**待测风险**：需要进入任务、事件或玩家体验后判断的问题。

禁止使用一个笼统的“验收通过”覆盖不同证据。

## 6.1 文案工具

使用 Python 标准库脚本 [card_tools.py](scripts/card_tools.py)。脚本读取当前字段快照；本轮使用更新真源时，通过 `--fields` 提供对应快照。

```bash
python scripts/card_tools.py check 角色草案.md
python scripts/card_tools.py check 人工角色卡.md --preserve-layout
python scripts/card_tools.py check 角色草案.md --partial
python scripts/card_tools.py render-notion 角色草案.md
python scripts/card_tools.py compare 原稿.md 回读稿.md
python -B -m unittest discover -s tests -v
```

标准完整卡使用“字段／内容／要求”三列表格。脚本同时兼容旧版“字段／要求／内容”及已有人工稿两列表格，用于读取和迁移旧稿；兼容能力不改变 v8.1 的标准输出格式。

数值占位默认识别“待定”“未设定”“占位”及其推测标记；用户自定义占位使用 `--placeholder` 指定。五项数值说明只对四列表格执行机械核对。

公开特质、弱线索的条目数量由脚本辅助检查；同义重复、人物侧面独立性、复杂版式与字段归属仍需正文审查。

命令默认只读输入并输出结果，不覆盖文件、不联网、不写 Notion。格式转换遇到未支持结构时返回错误，不能静默丢失正文。

## 6.2 Skill 迭代验证

仅在维护本 Skill 时读取 [泛式回归案例](references/regression-cases.md)。角色设计与完整制卡分别使用对应泛式 example 验证输出边界和格式。

验证使用泛式或隔离输入，不修改真实角色池。只验证本次改动直接影响的行为；额外测试需要具体风险触发。

# 7.外部发布与关联影响

①用户要求聊天输出时直接交付。写入文件、Notion 或仓库时遵守指定目标与范围。

②写入前读取目标最新内容、ID 与版本，将人工改动合入底稿。无法裁决的冲突只暂停相关写入。

③只发布获授权角色及必要索引。关联角色、任务、事件和 Result 的影响可以列出，修改对应资产需要单独授权。

④Notion 使用当前工具支持的原生标题与表格。局部更新采用准确替换区域，保留子页、属性和无关内容。

⑤推测标记完整保存。发布成功不改变内容的确认状态。

⑥写后回读并核对正文、数值描述、推测标记、版本及必要索引。报告实际完成与未完成项。

# 8.交付结束

优先交付用户当前需要的正文、局部修改或发布链接。只补充影响使用的冲突与未确认项；完成后停止。

示例与测试使用经过验收的泛式角色称谓和关系类型，只承担结构、颗粒度与行为边界示范，不属于项目角色真源。正式角色卡按当前任务中的真实角色资料生成。
