# guild-today-char-card

## Purpose

用于创建、补全、修改与审查《今日公会照常营业》的正式角色卡。

核心目标：

`理解设计目的 → 建立人物 → 让人物进入游戏 → 检查实际效果`

角色设计应能够连接项目核心循环，但不同角色可以进入不同环节、承担不同程度的玩法功能。

Skill 评价角色是否实现其设计目的、是否符合当前真源、是否能够在游戏中成立。

---

# 1.适用范围

本 Skill 用于：

①.创建新角色。

②.补全已有角色。

③.修改已有角色。

④.审查角色设计。

⑤.根据已经确认的角色正文填写正式角色卡字段。

⑥.在当前任务明确进入结构化阶段时，协助生成程序字段。

---

# 2.开始工作前

## 2.1 确定当前任务

先确认：

`当前角色`

`任务类型`

`用户本次要求`

`允许修改范围`

`输出要求`

`角色设计目的`

用户已经明确设计目的时，直接采用。

用户明确提出新的角色设定、修改决定或裁决时，该决定作为当前任务中的最新事实。

用户仅要求审查、讨论、格式调整或限定工作范围时，保持现有角色事实。

## 2.2 读取真源

先读取：

`references/source-map.md`

根据当前任务读取对应正式真源。

角色工作通常需要确认：

`当前项目真源`

`当前角色池`

涉及已有任务、事件、Result、公共规则时，再读取对应领域规则真源与具体资产真源。

角色字段的日常填写、解释与审查优先读取：

`references/character-card-fields.md`

以下情况再读取 Notion《角色卡字段口径》当前真源：

①.用户要求检查最新字段口径。

②.字段 reference 内容存在疑问或与其他正式资产冲突。

③.当前任务涉及尚未冻结的字段规则。

④.维护或更新 `references/character-card-fields.md`。

历史资料只在当前任务要求追溯、比较或取材时进入工作范围。

## 2.3 读取字段参考

需要填写、解释或审查正式角色卡字段时，读取：

`references/character-card-fields.md`

该文件是角色字段真源的随 Skill 快照，顶部记录快照来源、日期与来源状态。

正常工作直接使用该快照。

当出现 2.2 所列情况时，读取 `source-map.md` 指向的当前 Notion《角色卡字段口径》进行裁决。

若快照与当前 Notion 真源发生冲突，以当前 Notion 真源为准，并在本次任务涉及维护 reference 时同步更新快照。

# 3.设计目的优先

## 3.1 设计目的

角色创作和审查首先回答：

> 这个角色希望给玩家带来什么人物体验？

设计目的可以来自用户明确要求，也可以从已有正式人物内容中归纳。

例如：

`让玩家逐渐发现她的真实动机`

`提供稳定可靠的队伍核心`

`表现普通冒险者的日常生活`

`制造难以控制的派遣风险`

`让玩家发现这个人确实始终善良`

`表现一个从始至终坚持同一价值的人`

“设计目的”是本 Skill 的工作变量。

它用于指导创作、决定展开深度和执行验收。

它不自动等同于正式角色卡字段中的“叙事定位”。

填写“叙事定位”时，应按照当前角色卡字段口径处理。

## 3.2 人物结构应服务设计目的

角色可以：

`复杂`

`简单`

`透明`

`神秘`

`稳定`

`变化`

`善良`

`阴暗`

`矛盾`

`从一而终`

隐藏面、弱点、秘密、成长、违抗、冲突等结构应在当前角色需要时使用。

角色缺少某种常见人物结构时，应先判断这种缺失是否影响设计目的。

只有产生实际影响时，才将其作为问题提出。

# 4.创作边界

## 4.1 已确认内容

创作应继承：

①.用户当前已经明确的决定。

②.项目真源中的现行规则。

③.《当前角色池》中的正式角色事实。

④.当前任务直接涉及的其他正式资产。

用户当前明确修改某项角色事实时，该修改作为当前任务的最新事实；《当前角色池》继续裁决尚未被本次明确修改的角色内容。

## 4.2 开放创作空间

真源留白、且属于当前角色自身范围的内容，可以正常创作。

例如：

`生活习惯`

`成长经历`

`职业经历`

`行为特点`

`价值判断`

`兴趣`

`具体动机`

`生活需求`

创作内容应与现有事实兼容，并服务当前角色设计目的。

## 4.3 公共未决内容

涉及：

`公共系统规则`

`统一状态规则`

`公共判定公式`

`尚未冻结的字段契约`

`项目级世界制度`

时，应读取对应真源。

当前仍未确定的部分保持为待定，并继续完成角色自身可以确定的内容。

---

# 5.角色创作 Workflow

## 5.1 建立人物核心

根据设计目的确定：

①.这个人是谁。

②.当前如何生活。

③.什么最能解释这个人。

④.通常如何行动。

⑤.哪些情境会实际影响其行为。

这里的核心可以是：

`动机`

`原则`

`责任`

`欲望`

`信念`

`生活方式`

或其他能够支撑人物的因素。

## 5.2 建立任务外生活

对持续承担人物内容的角色，应检查是否具有足够的任务外生活基础。

可以从实际需要中建立：

`工作`

`经济`

`居住`

`习惯`

`兴趣`

`日常关系`

`烦恼`

`屏外持续发生的生活`

涉及现有角色的新增私人关系按 5.5 处理。

若当前角色缺少任务外生活基础，应向用户注明：

`当前角色尚缺少任务外生活基础`

并说明这会影响哪些人物表达。

该项本身不构成验收失败。

## 5.3 建立玩家认知

根据设计目的确定玩家目前应该知道什么。

检查：

①.公开信息是否准确服务当前设计。

②.能力与人物经历是否兼容。

③.公开特质能让玩家理解什么。

④.弱线索承担什么功能。

⑤.已有公开关系是否影响判断。

角色需要信息差时，可以设计逐步认识过程。

角色强调透明、稳定或坦率时，公开信息可以直接反映真实人物。

## 5.4 建立人物行为

根据实际角色选择合适结构。

复杂行为可以采用：

`核心因素 → 情境 / 条件 → 选择 → 行为 → 后果`

稳定型人物可以采用：

`核心原则 → 稳定行为`

存在隐藏行为结构时，可以依据当前角色卡字段口径进一步组织。

重点检查：

> 实际行为是否符合这个角色，以及玩家能否通过游戏内容理解这种行为。

## 5.5 处理私人关系

用户明确要求生成某项私人关系时，可以结合双方正式角色内容进行设计。

用户未明确要求生成私人关系时：

`新产生的私人关系 → 暂定`

暂定关系只作为候选方案，不直接成为《当前角色池》中的正式事实。

当《当前角色池》已经拥有足够多的角色，可以形成有依据的关系候选时，应结合：

`经历`

`职业`

`生活`

`性格`

`已有接触`

判断是否存在值得建立的私人关系。

存在有价值的候选时，应向用户提出具体关系建议，例如：

> 是否考虑建立 XXX 与 XXX 的私人关系？

“角色池足够”根据实际可连接角色判断，不设置固定人数。

涉及已有正式角色的新关系时，应同时检查双方角色事实。

## 5.6 检查派遣价值

角色承担派遣功能时，应回答：

①.玩家为什么会想派这个角色。

②.人物能力、经验、性格、状态或关系会带来什么实际差异。

③.这种差异如何进入任务体验。

差异可以表现为：

`任务处理`

`结果`

`成本`

`信息获取`

`持续后果`

`报告反馈`

检查具体任务时：

`唯一性 = 否`

该任务属于可重复生成的通用任务。检查当前角色的派遣价值即可，无需证明该任务为什么还应选择其他角色。

`唯一性 = 是`

检查角色优势是否符合该任务与人物设计，以及是否影响该任务原本希望提供的决策内容。

某个角色成为单项任务中的最佳人选，本身不构成角色设计问题。

## 5.7 建立需要的信息出口

角色拥有需要逐步认识的内容时，应考虑玩家通过什么渠道获得信息。

可以来自：

`角色档案`

`弱线索`

`派遣表现`

`报告`

`通讯`

`关系`

`事件`

`状态变化`

`档案更新`

当前已经进入实际玩法的隐藏内容，应提供足够的理解依据。

未来内容只需要保留当前有价值的方向。

透明型角色可以省略隐藏揭露链。

## 5.8 填写正式字段

人物设计成立后，再按照：

`references/character-card-fields.md`

填写正式角色卡。

字段使用原则：

①.必填字段按当前口径填写。

②.选填字段根据人物实际需要使用。

③.特殊角色字段在人物自然产生对应设计时使用。

④.自动生成字段交由对应流程处理。

⑤.程序字段在角色正文确认并且当前任务进入结构化阶段时处理。

字段用于承载人物设计。

---

# 6.关联资产与影响追踪

角色修改影响已有资产时，应列出直接影响。

例如修改：

`核心动机`

可检查：

`行为逻辑`

`已有特殊行为`

`已有关系行为`

`已有任务表现`

修改：

`公开特质`

可检查：

`玩家认知`

`弱线索`

`实际行为`

修改：

`关键关系`

可检查：

`双方角色事实`

`关系触发`

`特殊组合`

`争执`

`关系变化`

影响进入已有任务、事件或 Result 时：

`列出资产 → 说明受影响内容`

当前任务包含对应资产修改时，再进入该资产的正式修改。

角色 Skill 负责发现影响。

对应资产真源负责该资产的正式内容。

---

# 7.程序字段边界

角色正文负责自然语言人物设计。

程序字段负责把已经确认的正文结构化为：

`条件`

`效果`

`状态变化`

`计数器`

`资产引用`

工作顺序应保持：

`人物设计 → 正文确认 → 程序结构化`

程序字段中的规则应能够追溯到已经确认的正文内容。

具体字段定义和当前公共执行规则读取对应 reference 与正式真源。

---

# 8.验收

验收只判断当前设计实际需要解决的问题。

## 8.1 设计目的

检查：

①.设计目的是否清楚。

②.当前人物内容是否支持该目的。

③.玩家是否有机会获得预期人物体验。

## 8.2 人物

检查：

①.主要行为是否能够由人物自身解释。

②.正式字段是否共同描述同一个人。

③.已有矛盾是否有合理来源。

## 8.3 玩家认知

检查：

①.玩家应该知道的信息是否有效传达。

②.需要隐藏的内容是否拥有合适的信息差。

③.需要透明的内容是否准确表达。

## 8.4 游戏作用

检查角色当前承担的游戏功能是否能够实际运行。

例如承担派遣判断时，应有足够派遣信息。

承担特殊行为时，应有可理解的行为依据。

承担隐藏揭露时，应有有效的信息出口。

角色只需完成与自身设计目的和当前内容有关的功能。

## 8.5 实质问题判定

以下情况属于实质问题：

①.角色内容与对应正式真源直接冲突。

②.人物出现无法由现有设计解释的直接矛盾。

③.角色设计无法实现用户明确的设计目的。

④.角色承担某项实际玩法功能，却缺少该功能运行所需的信息或设计。

其他问题根据当前设计目的判断影响，并作为：

`需要注意`

或：

`可选增强`

向用户说明。

---

# 9.输出规则

默认只输出当前任务要求的范围。

正式角色卡按照当前字段口径输出。

局部修改只处理对应内容及直接影响。

审查结果区分：

`实质问题`

`需要注意`

`可选增强`

私人关系尚未确认时标记：

`暂定`

公共未决内容标记具体依赖。

除非当前任务明确要求，角色工作结束后不自动扩展到任务、事件、Result 或公共系统设计。

---

# 10.最终原则

`设计目的 → 人物 → 玩家认知 → 游戏表达 → 验收`

Skill 用于帮助角色设计成立。

它负责约束真源、边界和质量。

具体人物应该长成什么样，由当前角色的设计目的决定。
